# 知识结构工具（demo v0）

> 大多数知识工具最后都干成了一件事：把你不知道的东西，编成看起来知道的样子。

---

## 它是什么

一套**只给结构、不给内容**的知识节点规格，外加一个只读校验器。

- 每个节点是一个 `.md` 文件：YAML front matter + 可选正文。可 `git diff`、可手工编辑、可用文本编辑器打开
- 节点挂在**两个索引**上：`title` 是概念索引，`cues` 是情境索引
- **情境索引才是调用入口。** 概念索引问"这东西叫什么"；情境索引问"我现在处在哪种处境"。
  后者才是入口，因为专家靠"认局"触发知识，不靠概念树
- 校验器只回答"结构自不自洽"，不回答"这条知识对不对"
- 零运行时依赖：Python 3.9+ 与 PyYAML。无数据库、无图库、无 RDF、无常驻进程

## 它不是什么

⭐ **这一节比上一节重要。**

- **不生成答案。** 没有检索，没有问答，没有"根据你的问题推荐"
- **不填内容。** 一个字段都不知道该填什么时，它就该是空的。这个工具的全部设计都在保住这个"空"
- **不替判断。** 校验器不会说"建议采信哪一条"，也不会说"这条更权威"。权威度不进任何排序
- **不构成任何专业建议。** 仓库里没有一个字的真实领域内容
- **这不完整。** 六层是能力上限，不是使用要求
- ⚠️ **这是一个结构规格的可行性 demo，不是一个可用产品。**
  没有检索、没有内容库、没有验证。它证明的只有一件事：这套约束能不能落成能跑的代码

### 我们不规定什么（没限制，也要写清楚）

上一节说的是"不做什么"，这一节说的是**"不管什么"**。两件都得写，
否则你会以为有个规矩，然后为了守它去改自己的文件。

- **案例的正文怎么写，不校验。**
  [SPEC](SPEC.md) 的 ⑤ 案例层写作「情境特征 + 考虑过的选项 + 理由 + 结果 + 反事实」，
  但这五段里**只有情境特征有字段承载**（就是 `cues`）。其余四段只能写进正文，
  而**正文是自由的**——写几段、用什么小标题、顺序怎么排，都由你定。
  实测：一个正文**完全空着**的 `案例` 节点，照样通过校验（退出码 `0`，零报告）。
  也就是说，`type: 案例` 只保证"它自称是案例"，**不保证它有案例的形状**。
- **`案例` 的 `relations` 往哪指、朝哪个方向指，不约定。**
  SPEC 的方向约定表只有 5 行，覆盖判断点、条件、例外、立场、论据、概念这 6 种 type——
  案例不在其中。案例指向谁、指哪个类型、朝哪个方向，都不算错。
  校验器对案例的 `relations` 只查两件事：
  **引用的 id 存不存在**、**有没有成环**（R3）。方向对不对，它查不了，也不打算查。

**一句话：这两块没有限制。** 你按自己的方式写，不会因此报错——
代价是你也拿不到保障，校验器不会告诉你案例写全了没有。

> 这两条是**有意的**，不是没做完。补规则等于让人为了过校验回头改自己的文件，
> 而案例层本来就是可选的表达力（六层是能力上限，不是使用要求）。

### ⚠️ 关于"模型代填"——这是本项目的立项根基，不是一条功能取舍

**模型替人填内容，这个项目就没有存在的理由了。**

一个知识结构工具最容易死的地方，是它自己动手把空格填满——因为"填满"看起来比"留空"更有用。
一旦如此，它就退化成了又一个"把不知道的编成看起来知道的样子"的机器，而后者正是它要反对的东西。

所以这条规矩是**双重拦截**的，两道都不可绕过：

| 拦截点 | 手段 |
|---|---|
| **校验器** | 规则 R7：`filled_by` 是模型的文件里出现 `evidence_status: 已验证`，直接报 ERROR，且文案点明"**疑似模型代填**" |
| **README（此处）** | 任何填充器——人、模型、脚本——都必须如实写 `filled_by`。模型填的写 `模型(vX)`，本仓库示例一律写 `模型(示例数据)` |

**如果你想用 AI 帮你填充这个仓库，请让它把 `filled_by` 写成它自己。**
那不是禁止，是留痕。留痕之后，别人一眼就知道这条知识该被多谨慎地对待。

**`filled_by` 的值不设限制，这是有意的。** 校验器只要求这个字段存在，不规定里面能写什么——
本仓库用的 `人` / `模型(vX)` 是一种**约定，不是白名单**。下游要接自己的填充器
（别的模型、脚本、机构流程），自己定义取值、在自己的校验里加约束即可，不必改这份结构。

**这里只保证一件事：填了就得留痕，且留的痕要能看出是谁填的。**

唯一的例外是 `未填充`——它不是一种署名方式，而是一个**事实断言**："这个节点还没人填过"。
所以它有一个可以被结构校验的含义：**声明了 `未填充` 的节点里不能有任何内容**，否则报 `R8`。
没有这条，`未填充` 就成了"填了但不署名"的合法通道，
上面那句"填了就得留痕"也就只剩一句自觉。

一旦出现**未留痕的模型填充**，本项目的第一条硬规矩即告失效——那比校验器报错严重得多。

## 5 分钟上手

```bash
git clone https://github.com/aic-123/ks-demo.git
cd ks-demo
pip install -r requirements.txt      # 只装一个 PyYAML
python validator/validate.py ./samples
```

**先验一下校验器自己：** `python validator/validate.py --self-test`（不读数据，只跑内置断言）。

退出码：有 `ERROR` 为 1，仅 `WARN` 为 0。
**`samples/` 是干净通过的，退出码 `0`。** 留白的地方只产生 `WARN`——那不是错误，是这个工具要展示的东西本身。

### 还欠什么：待填清单

```bash
python validator/validate.py ./samples --todo
```

同一个校验器，另一个视角：它不报"哪里坏了"，只列**"还欠什么"**——
`cues` 为空、`source.ref` 为空、`notes` 标了"待填"的节点，连同它们已经挂上的关系。

```bash
$ python validator/validate.py ./samples --todo
待填清单 —— 只列缺口，不给答案，不按任何权威度排序。

samples/roommate-noodles/arg-0102.md
    论据　「沉默的原因里，没有一条是同意」
    · 缺 source.ref —— 说不出这条知识从哪来
    · 缺 notes —— 自己标记了「待填」
    · 已挂上：stance-0102

samples/roommate-noodles/case-0101.md
    案例　「他没回我，我就吃了」
    · 缺 source.ref —— 说不出这条知识从哪来
    · 已挂上：judge-0101 → case-0001

samples/roommate-noodles/claim-0101.md
    断言　「问过之后吃，比不问就吃更接近做对」
    · 缺 cues —— 没有情境索引，认局的时候调不出这个节点
    · 缺 source.ref —— 说不出这条知识从哪来
    · 缺 notes —— 自己标记了「待填」
    · 已挂上：issue-0101
...
扫描 23 个节点，21 个存在待填项。
注意：列出缺口不等于出错。「未验证 + 无出处」是合法状态，列在这里只因为它还欠着。
这份清单只说「还欠什么」，不说「该填什么」。填什么、由谁填，由人决定。
```

（上面**只截了前 3 个节点**，实际会列出 21 个。省略号处的输出是真实存在的，不是省略的写法。）

注意第二个：那是一个**案例**，它唯一的缺口就是 `source.ref`。这正说明"空值合法"不是空话——
一个说不出出处的案例照样是合法节点，它只是**不能被当成依据**。这跟"写坏了"是两回事。

**注意最后那句**：这份清单**不给答案**。它告诉你哪里空着，但"该填什么"必须由人来决定——
这正是"空值合法"这条硬规矩的可用出口。退出码恒为 `0`：缺口不是错误。

它长这样：

```
                        ┌──────────────────────────────────────┐
                        │  cues     情境索引  ← 真正的入口     │
                        │  title    概念索引  ┐                │
                        │  aliases  别名      ┘ ← 事后才用得上 │
                        └────────────────┬─────────────────────┘
                                         │
                                ┌────────▼─────────┐
                                │  节点 = 一个 .md  │
                                │                  │
                                │  id              │  前缀-四位序号
                                │  type            │  九种之一
                                │  scope           │  含"不适用"
                                │  source.ref      │  ← 可以是空的
                                │  evidence_status │  ← 默认 未验证
                                │  relations ──────┼──▶ 另一个节点
                                │  filled_by       │  ← 谁填的，如实写
                                └──────────────────┘
                                         │
                          ┌──────────────┴──────────────┐
                          │  validator/validate.py      │
                          │  只报告，不写文件，不修复    │
                          └─────────────────────────────┘
```

## 示例骨架

`samples/` 下两个**完全虚构**的领域，共 23 个节点（11 + 12）：

| 领域 | 平时的样子 |
|---|---|
| [`samples/router-reset/`](samples/router-reset/) | 路由器什么时候该重启 vs 该报修 |
| [`samples/roommate-noodles/`](samples/roommate-noodles/) | 室友的泡面该不该吃 |

两个领域都**恰好覆盖六种形状**：

1. 一个完整的**判断点**：≤4 个变量 + 阈值 + 例外
2. 一个**不收敛的分歧**：议题 + 两个对立立场 + 各自论据
3. **至少 2 处明晃晃的空值**：`source.ref: ""`、`evidence_status: 未验证`、`notes: 待填`
4. 一条带 `relations` 的**例外覆盖**关系
5. **概念节点带 `aliases` 别名**（词汇层的 altLabel）：如「假死」的别名是"假掉线""假连接"——
   这正是"同一概念别三种叫法"的落地位置
6. 一个**案例**（⑤ 案例层）：情境特征 + 考虑过的选项 + 理由 + **空着的结果** + 反事实。
   两个案例用 `relations` 连了起来（`case-0101 → case-0001`，**单向**）——
   它们不是同类处境（一个是路由器，一个是泡面），而是**同类空值**：
   结果未知，所以能被检索到、不能被照抄。
   （案例正文的形状和 `relations` 方向都**不受校验**，见上面「我们不规定什么」。）

**所有示例内容的 `filled_by` 一律是 `模型(示例数据)`**，`evidence_status` 一律是 `未验证`。
`notes` 只有三种写法：标明"形状演示，非真实知识"、留给 `--todo` 的"待填"标记、
以及两个案例节点上的 `"演示用，非事件记录"`——**它们不是任何真实发生过的事**。
没有真实教材、没有论文、没有人名、没有机构名、没有产品型号。这些是我编的，请当成形状看，不要当知识看。

**这个目录是干净通过的**（退出码 `0`）。里面只有 3 处 `cues: []` 产生的 `WARN`——
那是留白的正常状态，不是错。

### 想看校验器能抓什么：`samples-broken/`

```bash
python validator/validate.py ./samples-broken
```

[`samples-broken/`](samples-broken/) 是**故意的错误集**：每条规则一个文件，
跑一遍 R1–R8 **全部命中**（10 个节点，ERROR 8 / WARN 1，退出码 `1`）。
每个文件的正文都写明了"错在哪、为什么算错、怎么修"。

两个目录的分工：

| 目录 | 是什么 | 退出码 |
|---|---|---|
| `samples/` | **形状示范**——结构完整，干净通过 | `0` |
| `samples-broken/` | **规则示范**——每个文件故意违反一条规则 | `1` |

分开的理由很简单：第一条命令应该是绿灯。
想看清楚校验器的火力，再去看第二个目录——**不必让"上手"和"报错"挤在同一条命令里**。

## 给懂得的玩家

> 这只是一个 demo。架构（六层）是能力上限，不是使用要求——你可以合并、裁剪、替换任何一层，
> 只要保持四条硬规矩。

四条硬规矩：

1. 不代填内容——不知道就留空
2. `filled_by` 如实标注
3. `evidence_status` 不接受自声明
4. 权威度、来源可信度、机构名望，不进任何排序逻辑

层可以扔，这四条不能扔。扔了任何一条，这个仓库就没有存在的理由了。
