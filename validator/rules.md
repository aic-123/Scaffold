# 规则说明（人看的版本）

校验器只做两件事：**报告「结构是否自洽」**，以及**列出「还欠什么」**。
它不回答「这条知识对不对」「该信哪一条」——那不是它能回答的，也不是它被允许回答的。

两种用法：

| 用法 | 做什么 | 退出码 |
|---|---|---|
| `validate.py ./samples` | 报告结构问题（R1–R8） | 有 `ERROR` 为 1，仅 `WARN` 为 0 |
| `validate.py ./samples --todo` | **待填清单**：只列缺口，不给答案 | 恒为 `0` |

八条规则，三个等级：

| 级别 | 含义 | 影响退出码 |
|---|---|---|
| `ERROR` | 结构坏了，必须处理 | 是（退出码 1） |
| `WARN` | 结构能跑，但有缺口 | 否 |
| `INFO` | 说明性提示 | 否 |

**校验器是只读的。** 它不写文件、不改字段、不自动补全、不"帮你顺手修一下"。
空值就是空值——它只报告，修不修、怎么修，是人决定的。

---

## R1 · 孤立节点

**查什么**：一个节点的 `relations` 是空的，同时也没有任何其他节点指向它。

**为什么**：一个谁也不连的节点，既调用不到，也反驳不了。它不参与任何推理，等于没写。

**豁免**：`概念` 类型豁免。词汇层本来就是被别的层引用的，单独站着是正常的。

**怎么修**：接上它该解释的现象；或者承认它什么也解释不了，删掉。

---

## R2 · 缺出处

**查什么**：`source.ref` 为空，但 `evidence_status` 不是 `未验证`。

**为什么**：这是一条逻辑自洽问题，不是内容对错问题。「我声明这是一条假说」和「我说不出它从哪来」
不能同时成立——假说也是要有出处的，出处标明了它是谁的假说。

**不报的情况**：`evidence_status: 未验证` 且 `source.ref: ""`。这是合法状态，
正是本设计要保住的那个"不知道"。空值在这里不报错。

**怎么修**：补上出处；补不出来就把 `evidence_status` 改回 `未验证`。

---

## R3 · 循环依赖

**查什么**：`relations` 构成环。报告里会给出完整环路：`a → b → c → a`。

**为什么**：环上的节点互为前提。往下读的时候会无限循环，往上追溯的时候也没有一个落脚点。

**最常见的一种环，是本来就写错了**：把 `立场 → 论据` 和 `论据 → 立场` 两边都写了。
`relations` 是**有向**的，一个方向就够，反方向请写在正文里。详见 SPEC.md「relations 的方向约定」。

**怎么修**：删掉环上任意一条 `relations`，保留信息量更大的那个方向。

---

## R4 · 类型与字段不匹配

**查什么**：

- `type: 判断点`，但正文里没有 `变量：…` 声明
- `type: 判断点`，但声明的变量超过 4 个
- `type: 立场`，但 `relations` 里没有指向任何 `议题`
- 十一个必填字段里有缺失的

**为什么**：`type` 不是标签，是承诺。写 `判断点` 就等于承诺"我能被拿去对照现实用"——
声明不出看哪几个变量，这个承诺就是空的。写 `立场` 就得有议题可站，否则它是一个断言，不是立场。

**4 个变量的上限**：超过 4 个变量的东西不叫判断点了，叫"情况很复杂"。
上限逼你把真正起作用的那几个挑出来。

**怎么修**：补正文、砍变量、补 `relations`，或者换一个更诚实的 `type`。

---

## R5 · id 冲突或格式错

**查什么**：

- id 格式不是 `前缀-四位序号`
- 同一个 id 出现两次
- id 的前缀与 `type` 对不上（如 `type: 概念` 却写成 `arg-0001`）
- `type` 不在九种之内
- `relations` 指向一个不存在的 id
- 文件的 front matter 根本解析不了

**为什么**：id 是这个仓库里唯一的硬链接。id 一乱，`relations` 就全成了猜谜。

**怎么修**：按 SPEC.md 的映射表改前缀；重复的换成领域编号段里没用过的号；悬挂引用改拼写或先把节点建出来。

---

## R6 · 情境索引缺失（警告级）

**查什么**：`cues` 是空数组。

**为什么**：情境索引才是调用入口。没有 `cues` 的节点，只有在**已经知道它叫什么**的时候才找得到——
而需要它的时刻，恰恰是你还不知道它叫什么、只知道"我现在遇到了这么个情况"。

**为什么只是警告**：写不出 `cues` 是常态，不是错误。逼着人现编一句症状，比留空更糟。
留空至少是诚实的，而且校验器会一直提醒你这里还欠着一句。

**怎么修**：写下"当事人会怎么描述自己的处境"，用他的词，不用你的词。

---

## 附：`aliases` 与 `cues` 不是一回事（不单列规则，但最容易写错）

两个字段都装"词"，装的是两种完全不同的词。混用会让情境索引失效。

| 字段 | 回答的问题 | 例子（以 `con-0001`「假死」为例） |
|---|---|---|
| `aliases` | 这东西**还叫什么名字** | "假掉线"、"假连接" |
| `cues` | 当事人**处在哪种处境** | "灯是亮的，但网没了"、"管理页打不开，指示灯却一切正常" |

**判断标准只有一条**：这句话能不能用来描述"我遇到了什么"。
- 能 → 它属于 `cues`
- 它只是在给同一个东西换个叫法 → 它属于 `aliases`

**`aliases` 为空不报警。** 不是每个概念都有别名，空数组是合法且常见的状态。
这与 `cues` 不同——`cues` 是调用入口，缺了它节点就调不出来，所以 R6 要提醒。

---

## R7 · 状态越权自声明（重点）

**查什么**：`evidence_status` 出现 `已验证`，或者出现合法值之外的任何东西。

**为什么**：`已验证` 不是一种"我觉得对"的状态，是一个**授权**。
它只能由验证方通过 hooks 契约写入（见 `hooks/validator-interface.md`）。
任何人手写这个值，都是在往这个字段里塞一句自己没资格说的话。

- 手写文件里出现 → `ERROR`：该状态只能由验证方通过 hooks 授予，不可手工写入。请改为 `未验证`。
- `filled_by` 是模型的文件里出现 → `ERROR`，且文案会**点明"疑似模型代填"**。

**用户可写的值只有五个**：`已确立` / `假说` / `有争议` / `已淘汰` / `未验证`。默认 `未验证`。

**`--allow-verified` 开关**：默认关闭。启用后 `已验证` 不再报错，降级为 `INFO`。
该开关**只允许用于 hooks 授权的输出目录**。在普通目录上开它，等于把这条规则关掉，
那这个仓库就没有存在意义了。

**怎么修**：改回 `未验证`。要升级就走 hooks 流程。

---

## R8 · 未填充声明与内容矛盾（本仓库新增，设计稿七条之外）

**查什么**：`filled_by` 写的是 `未填充`，但节点里已经有内容。

**为什么**：`filled_by` 的取值本身**不设白名单**——写 `人`、写 `模型(vX)`、写
`机构(某流程)`、写 `脚本(import-v2)`，校验器都不管。这是有意的：下游要接自己的填充器，
不该为了换个填充器去改结构。

但 `未填充` 是个例外。它不是一种"署名方式"，而是一个**事实断言**：
*这个节点还没人填过*。所以它有一个可以被结构校验的含义——

> 一个说"没人填过"的节点，里面就不该有东西。

这条规则守的正是立项根基里的第 2 条（填充者留痕）。允许 `未填充` 与内容同时出现，
等于给"填了但不署名"开了一条合法通道：内容摆在那儿，`filled_by` 写 `未填充`，
校验器一声不吭。那第 2 条硬规矩就只是句口号了。

**什么算"有内容"**：`title`、`scope`、`notes`、`aliases`、`cues`、`relations`、
`source.ref`、正文，任一非空即算。`source.kind` 写 `未知` **不算**——那是"不知道"，
不是内容；写了具体值（教材 / 论文 / …）才算。

**怎么修**：要么如实写是谁填的，要么把内容清空。二者只能选一个。

**注意 R7 与 R8 的区别**：R7 管的是 `evidence_status`（"有人验过了"这句越权的话），
R8 管的是 `filled_by`（"没人填过"这句假话）。两句都是自我声明，都得跟文件里的事实对得上。

## 执行期的判断（三条，需要设计方确认）

设计稿给的是七条规则的**意图**，有两处意图明确、但字面没写全。校验器按意图实现了：

1. **R4 里包含了"必填字段缺失"**。字段清单写了"必填"，但七条规则里没有一条管它。
   不检查的话，"必填"就只是一句注释。
2. **R5 里包含了"悬挂引用"**（`relations` 指向不存在的 id）。规则名叫"id 冲突或格式错"，
   而指向一个不存在的 id，就是引用的 id 错了。
3. **R8 是本仓库新增的第八条规则**，设计稿里没有。它守的是立项根基第 2 条
   （填充者留痕）——没有它，`filled_by: 未填充` 会成为"填了但不署名"的合法通道。

前两条是**可以关掉的**：若设计方认为超出了 R1–R7 的范围，删掉 `validate.py` 里对应的两个循环即可，
其余规则不受影响。

第 3 条不同——它是**加出来的规则**，不是对既有规则的补注。设计稿只有七条，
R8 的存在需要设计方明确认账（或者明确否掉）。否掉的代价是：
`filled_by` 会退回成"只要求字段存在"的纯注释字段，
而"留痕"这条硬规矩就只剩 README 里的一句自觉。

> **已定案（2026-09-13）：另有两处"我们不规定"，且明确不补规则**——
> ① ⑤ 案例层的正文形状不校验；② `案例` 的 `relations` 方向不约定。
> 两者都写进了 README 的「我们不规定什么」一节，面向使用者披露。
> 理由：补规则等于让人为了过校验回头改自己的文件，而案例层本就是可选的表达力。
> 见 `SPEC.md` §一（relations 方向）与 §二（案例层形状）。

## 校验器不做的事

- 不判断内容对错，不给出"这条更可信"之类的结论
- 不做任何基于 `source.kind`、`source.ref`、机构名望的排序、加权、打分
  （排序键只有 `严重度、文件路径、行号`，见 `validate.py` 的 `report()`）
- 不写文件、不自动修复、不自动补全
- 不联网、不读数据库、不需要常驻进程
- 不检查"层"——六层是组织方式，不是节点属性，schema 里没有 layer 字段
- **不校验 `README.md`**（任何以 `readme` 开头的 `.md` 都跳过）——那是给人看的说明，不是知识节点
- **不规定 `filled_by` 能写什么**。`人` / `模型(vX)` 是约定不是白名单，写别的也不报错。
  唯一有结构含义的取值是 `未填充`，它受 R8 管——因为那是个事实断言，不是署名
- **不检查「案例」的形状**。⑤ 案例层要的是「情境特征 + 考虑过的选项 + 理由 + 结果 + 反事实」，
  但这五段里只有情境特征有字段承载（落在 `cues`），其余四段只能写进正文。
  实测：**正文全空的 `案例` 节点退出码 `0`、零报告**。也就是说 `type: 案例`
  现在只保证"它自称是案例"，不保证它有案例的形状。
  **已定案：不补规则。** 补了等于让人为了过校验改自己的文件。已写进 README 披露
- **不规定 `案例` 的 `relations` 往哪指、朝哪个方向指**。SPEC 的方向约定表只管五类关系，
  案例不在其中。校验器只查引用是否存在、是否成环——方向它查不了，也不打算查。
  代价（示例的写法不是约定）已在 `SPEC.md` §一 与 README 写明
